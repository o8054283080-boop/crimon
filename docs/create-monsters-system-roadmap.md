# クリエイトモンスターズ 育成・戦闘システム開発仕様

## 1. この文書の目的

この文書は、育成・戦闘システムを段階的に拡張する際の共通仕様と安全策を残す。実装時はこの文書に加え、`docs/design-concept.md` の「モンスターやスキルに役割を持たせる」方針を守る。

仕様の強さを次のように表す。

- **確定仕様**: 今後の実装が守る前提。変更する場合は、この文書と移行方針を同じPRで更新する。
- **暫定仕様**: 方向性は採用するが、数値・操作・細部は検証後に変更できる。
- **未確定・要検証**: 実装前にゲームデザイン、データ、UI、AIへの影響を決める。

## 2. 現行システム調査（2026-08-27、`f5f6ae9` 基準）

| 領域 | 主なファイル | 現在の責務・構造 |
| --- | --- | --- |
| モンスターデータ | `src/core/monster.ts`, `src/data/monsters.ts` | `MonsterTemplate` から属性別 `MonsterDefinition` を生成する。静的な基礎能力・3スキルと、所持個体を分離している。 |
| 所持個体・実効能力 | `src/core/monsterInstance.ts`, `src/core/stats.ts` | 星、レベル、経験値、装備、スキルレベル、継承スキルは個体に保存する。戦闘直前に `toBattleDefinition` で静的定義と合成する。 |

| クリエイト・スキル継承 | `src/game/monsterCreate.ts`, `src/web/views/monsterCreate.ts`, `src/web/main.ts` | 星6素材を消費し、スキル2または3の同じ枠へ1つだけ継承する。画面状態と永続状態は分離されている。 |
| ダメージ | `src/battle/damage.ts`, `src/core/skill.ts` | 攻撃力、スキル倍率、既存の参照値ベース補正、防御軽減、属性、クリティカル、装備補正の順で計算する。 |
| バフ・デバフ | `src/core/skill.ts`, `src/battle/unit.ts`, `src/battle/engine.ts` | スキル効果は判別可能なunion、継続中の能力増減は `ActiveEffect`、その他の状態は `BattleUnit` の専用フィールドで管理する。解除対象は効果種別ごとに実装されている。 |
| AI | `src/battle/ai.ts`, `src/game/pvpArena.ts` | 使用可能な最大番号のスキルを優先する簡易AI。対象は属性相性、HP比、対象種別で決める。アリーナでは編成評価用の効果分類も行う。 |
| セーブ | `src/game/playerState.ts`, `src/game/saveFile.ts`, `src/game/saveDurability.ts` | `localStorage` のv1キー、バックアップ、JSON書き出しを持つ。`normalizeLoadedState` が旧データの不足フィールドを補完する。ファイル版は新しすぎるversionを拒否する。 |
| UI | `src/web/main.ts`, `src/web/views/*`, `src/web/views/monsterCard.ts` | `main.ts` が画面状態・操作・保存を統括し、各viewがDOMを構築する。戦闘表示は `battleView` / `battleHud` とThree.js演出に分かれる。 |

### 現行の重要な境界

1. `MonsterDefinition` は図鑑・敵にも使う静的戦闘データ、`MonsterInstance` はプレイヤー所持個体である。
2. 永続的な育成値を戦闘へ反映する入口は原則 `toBattleDefinition` とする。ダンジョン等が `computeEffectiveStats` を直接呼ぶ箇所は、タイプ実装時に漏れを再調査する。
3. スキル効果の定義は `SkillEffect`、効果処理は `BattleEngine`、戦闘中状態は `BattleUnit` にまたがる。新状態は三者と表示・AI・解除判定を同時に確認する。
4. 読み込んだ永続データは必ず `normalizeLoadedState` 相当の移行処理を通す。

## 3. 将来仕様

### 3.1 クリエイト

**確定仕様**

クリエイトは次の4項目へ拡張する。

1. スキル継承
2. タイプ転生
3. 能力付与
4. 潜在覚醒

既存のスキル継承と既存個体を壊さず、機能ごとに段階導入する。

**暫定仕様**

- 個体固有の将来育成値は `MonsterInstance.development` 以下に集約する。
- 未利用の個体は未転生・0ポイント・未覚醒とし、現在の戦闘結果を変えない。

**未確定・要検証**

- 各操作の素材、費用、取り消し・振り直し条件。
- スキル継承の既存制約を4項目化後も維持するか。
- 4項目の画面導線、解放条件、確認画面。

### 3.2 タイプ

**確定仕様**

タイプは「攻撃」「体力」「防御」「補助」「妨害」の5種とする。保存値は表示文言から独立した安定ID（`ATTACK`, `HP`, `DEFENSE`, `SUPPORT`, `DISRUPT`）を使う。

**暫定仕様**

- タイプは将来、初期ステータスとレベルアップ時の成長へ補正する。
- 既存個体の初期値はタイプなしとし、補正を推測適用しない。

**未確定・要検証**

- モンスターごとの初期タイプ、転生時の選択可能範囲。
- 各タイプの基礎値・成長率・速度への補正値。
- 現行の文字列 `role` との関係。`role` を保存用タイプとして流用しない。

### 3.3 能力ポイント

**確定仕様**

- 1個体につき合計100ポイントをHP・攻撃・防御・速度へ自由に割り振れる。
- 4能力の配分を独立した数値として保存し、係数変更時にもセーブを書き換えず再計算できる構造にする。

**暫定仕様**

- 上限値 `ABILITY_POINT_BUDGET` と配分値を分ける。
- 能力への換算は戦闘定義の組み立て時に行い、保存値には換算後ステータスを焼き込まない。

**未確定・要検証**

- 1ポイント当たりの上昇量、能力別上限、整数丸め順。
- 獲得・解放条件、振り直し費用、UI操作。

### 3.4 潜在覚醒

**確定仕様**

- 新アイテム「覚醒オーブ」を使用する。
- モンスターごとにスキル1を強化する潜在能力を3候補用意し、1つ選択する。
- 選択結果は表示名ではなく安定IDで個体に保存する。

**未確定・要検証**

- 覚醒オーブの入手先、所持上限、消費数。
- 候補内容、再選択可否、既存のスキルレベル・継承との相互作用。
- 3候補をテンプレート単位、属性別、個体抽選のどこに置くか。

### 3.5 HP/DEF依存攻撃

**確定仕様**

HPまたはDEFを攻撃力とは独立した火力源として扱える式を導入する。目標形は次の通り。

- HP依存: `ATK × A + 最大HP × H`
- DEF依存: `ATK × A + DEF × D`

**暫定仕様**

- 係数はスキルデータ側に宣言し、ダメージ計算側にスキル固有分岐を増やさない。
- 既存の `scaleBonus` は「ATK倍率への上乗せ」であり上式とは意味が異なるため、移行時に別形式として追加する。

**未確定・要検証**

- A/H/D、上限、敵HP利用時のバランス、防御軽減との計算順。
- 既存スキルを新式へ移行する対象と時期。

### 3.6 新しい状態効果

**確定仕様**

- バフ: 被クリ率ダウン、我慢、反射、復活、無敵。
- デバフ: 挑発、強化不可、スキル使用不可、被クリ率アップ。
- 将来、バフ解除・デバフ解除の対象整理も行う。

**暫定仕様**

- 効果定義は判別可能なunion、戦闘中状態は明示的な残りターンとし、文字列比較だけで挙動を決めない。
- 新効果追加時は、付与確率・命中抵抗・免疫・解除・重複・延長・死亡時処理・AI・UIアイコンをチェックリスト化する。

**未確定・要検証**

- 我慢の最低HP、反射量と反射連鎖、復活HP、無敵と継続ダメージの関係。
- 挑発中の対象/スキル制限、強化不可の既存バフ更新、スキル使用不可と通常攻撃の扱い。
- 被クリ率補正の上下限と属性相性との関係。

## 4. 5段階の実装計画

1. **保存基盤（本タスク）**: 現行調査、仕様書、個体育成データの型・無効果デフォルト・旧セーブ補完・回帰テスト。
2. **タイプ転生**: データ定義、設定操作、基礎/成長補正を一つの純粋関数に実装。既存個体は補正なしを維持し、変更前後の内訳をUI表示する。
3. **能力付与**: 100ポイント制約と配分UI、振り直し、実効能力への変換を実装。係数はデータ/定数化し、境界値をテストする。
4. **潜在覚醒**: オーブ所持、候補データ、選択UI、スキル1への適用を実装。候補ID消失時のフォールバックを用意する。
5. **戦闘拡張**: 独立HP/DEFスケーリング、新バフ/デバフ、解除ルール、AI評価、戦闘/UI演出を効果ごとの小さいPRで追加する。

各段階で、既存テスト、型検査、ビルド、旧セーブfixture、新規状態の単体/戦闘テストを通してから次段階へ進む。数値調整と構造変更を同じPRに混在させない。

## 5. セーブ互換性規約

1. 保存フィールドを追加したら、新規作成値と旧データ補完値を同じfactoryから生成する。
2. 補完値は既存の戦闘結果・所持品・進行を変えない中立値にする。
3. 永続データには表示名、計算済み能力、候補配列そのものではなく、安定IDとユーザーの選択値を保存する。
4. fieldの改名・意味変更はその場の条件分岐ではなく、明示的なschema version移行とfixtureテストを用意する。
5. JSONファイル読込は構造検証後にnormalizeし、新しすぎる形式は従来通り拒否する。
6. 不明なタイプ/潜在IDを黙って別の効果へ置換しない。無効果で保持または安全に拒否し、復旧可能性を残す。

## 6. 次タスク開始時のチェックリスト

- この文書と `docs/design-concept.md` を読む。
- `MonsterDefinition` / `MonsterInstance` / `BattleUnit` のどの層の値かを決めてからフィールドを足す。
- `computeEffectiveStats` の直接利用箇所を検索し、戦闘入口ごとの適用漏れを確認する。
- localStorage、書き出しファイル、バックアップの全読込経路がnormalizeを通ることを確認する。
- 既存数値を変更する場合は構造PRから分け、変更理由と計測結果を `docs/balance-notes.md` に残す。
- UI追加時はモバイル幅、キーボード操作、選択中表示、破壊的操作の確認を検証する。
