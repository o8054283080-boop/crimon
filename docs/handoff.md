- 上限は**数**で持つ(`staminaPotionFarmBudget`。0 = 使わない)。

  貯めたい人は周回のたびに切り替えるしかなかった
- **「全部」は所持数ではなく印**(`STAMINA_POTION_UNLIMITED_BUDGET`)で持つ。
  所持数を焼き付けると、周回中に増えたぶんが使われない
- **ダイヤは絶対に自動で使わない。**尽きたら `STAMINA` で正常に終わる
- 「最大 ×◯回」も決めた数だけを数える

**数を見せる欄は、0でも出すこと。**消してよいのは「その機能自体がまだ無い」時だけ。

## 自動周回(一巡終わっている。決めた理由だけ残す)

- **1周の時間は実測の中央値そのまま。**倍率で割り戻さない。x8で3秒なら3秒/周。
  以前あった「最低30〜45秒」は、**速く倒せる編成を組んでも周回が速くならない**
  原因だったので外した。残っている1秒は速さの調整ではなく**暴走止め**
  (0秒だと「経過時間 ÷ 1周」が跳ね、復帰した瞬間に数万回ぶんの処理権が生まれる)
- **周回中でも他の戦闘へ入れる。**スタミナの取り合いは起きない——
  既存実装が1周ごとに最新の控えを見てから次の1戦を始める作りで、前払いをしていない
- 報酬は**正式なクリア報酬処理**を通す。簡易テーブルを作らない

## 戦闘演出(未着手。調査だけ済み)

**コードに書いてある大きさの値は、そのままでは効いていない。** これを知らずに数値を
いじると時間を溶かすので、先に読むこと。

- 板1枚の最大は「画面の高さの16%」で頭打ち。実測で約1.63ワールド単位。
  つまり `endScale: 6.5` のような指定は切り捨てられ、**衝撃波の輪は指定の1/3の大きさでしか出ていない**
- 板の濃さには一律 0.42 が掛かる。これ以上薄くする方向の調整は意味が薄い
- **同時生存の上限が厳しい**。板は6枚で間引きが始まり、14枚で強制置換。帯は8枚。
  **同時に多くを出す設計は成立しない。** 多段化するなら「同時に増やす」のではなく
  時間的にずらして総数を保つこと

この制約は「派手さは明るさではなく間・形・timing で作る」という方針と技術的に一致する。

着手順の案:

1. `6976a3e` が足したテクスチャ7枚(`impactStar` / `crackDecal` / `rippleRings` /
   `godRay` / `voidCore` / `chevron` / `hexPanel`)が**1枚も接続されていない**。まずこれを繋ぐ
2. **打撃の三段化**。今は閃光・光球・輪が全部同時に発火して「一点集中」が無い。
   溜め → 衝撃(角のある形を極短命で) → 余韻(地面の亀裂を1.2秒残す)。
   跡は光ではないので、**加算の飽和を増やさずに時間を稼げる唯一の手札**
3. **大きい輪は板ではなく帯で描く**。線なので加算面積が増えず、安全に大きく鋭い輪が出せる。
   `6976a3e` が足した `grow` はこのためのものだが、まだ誰も使っていない
4. **属性差は色ではなく間で**。炎は3波を段階的にずらす、雷は溜めゼロで一撃、
   水は地面の波紋を時間差、光は上へ抜ける、闇は **NormalBlending** で背景を食う
   (周囲の加算光が締まって見えるので、明るくせずに強く見せられる)
5. `blunt`(打撃)が未実装。今は斬撃と刺突しか分岐が無い

**共通パラメータを上げる前に、上記3をやりきること。** それでも足りない場合、
上げるべきは板の大きさの上限ではなく**同時生存数の上限**の方(飽和の主因は
1枚の大きさより枚数のため)。

サンドボックスが速い。`probe.mjs eval` から
`import('/src/web/three/fx/vfxSandbox.ts').then(m=>m.mountVfxSandbox({set:'impact'}))`
で戦闘の進行を待たずに全エフェクトを並べられる。`freezeAt` で同じ瞬間を再現できるので、
変更前後の比較はこれを使うこと。

## モンスターの造形

### 頭部の作り直し(未着手。調査完了・手順まで確定)

**`addBeastHead` の影響範囲は竜と狼の2体だけ。** グリフォンは `buildGriffon` が頭を自前に組むので無関係。
アタッカー/ボス/デバッファーの役割ビルダー内の `addBeastHead` は、現13種が全員
専用骨格を持つため**どこからも呼ばれていない**。切り替えの検証は
`roster=wolf:DARK|dragon:FIRE` の1枚で足りる。

手順(そのまま実行できる形):

1. `BeastHeadOptions` に `hard?: boolean` を足す(`addTail` の `o: { hard?: boolean }` と同じ流儀)
2. `hard` のとき、`kit.ball` で組んでいる次を差し替える。
   **球を hull に置き換えるだけでなく、個数を減らして1本の連続した立体にすることが要点**
   - 頭蓋(roles.ts の球4〜5個)→ `kit.hull()` 1本。`sides: 7`、眉庇で `keel` を効かせて眉間の稜線を出す
   - 頬骨・眉庇(`lens` と `addFaceEyes` の brow)→ `kit.plate()`。`wrap` を頭蓋の横半径に
   - 下顎(`ball` 2個)→ `kit.hull()` 1本の角柱。咬筋は `plate`
3. `hard` が false のときは**現行コードをそのまま通す**。狼が角張らないことを画で確認
4. `hard: true` を立てるのは `buildDragon` / `buildBoss` / `buildDebuffer` / `buildAttacker`。
   **`buildWolf` は false のまま**

続けて: 顔の表情(`addFaceEyes` も全種別共有なので切り替え引数が要る)、
竜の胸の前端に `plateStack` を1本、`plate()` の頂点削減(1枚108頂点。手組みで約半分)。

**部品数を減らす作業は、描画回数を減らす作業と同じ方向を向いている。**
上の「球を減らして1本の立体にする」は造形と性能の両方に効くので、
性能を先にやるつもりでも、入口はここになる。

### トレントの枝が効いていない(要修正)

画面で確認したところ、ゴーレムとほぼ同じに見える。枝(`TEMPLATE_TRAITS.treant`)が
体に埋もれている。原因は2つ:

- ディフェンダーの骨格は頭が低く、左右に巨大な肩の岩塊がある。
  枝を `rig.head` の y=0.16 から生やしても肩の線を越えられない
- 葉叢に `p.accent` を使っているが、体色と差が付かず「体のこぶ」に見える

直し方: 枝をもっと長く・細くし、肩の線より明確に上へ出す。
葉叢は枝の先端に付ける(頭の周りではなく)。色は体色から離す。
確認は `roster=treant:GRASS,treant:WATER|golem:GRASS,golem:WATER` で
ゴーレムと並べて見ること。**小さい画像で判断しない**

### 体表の質感(2巡目完了。残りは翼膜の骨の影だけ)

完了済み: 暗部を青く明部を白く / 鱗に縁 / 結晶を内側から光らせる /
金属の濡れたハイライトと継ぎ目 / 遠くで線の模様を消す / 発光部を中心だけ白熱 /
布に襞 / 毛皮の房の縁 / 中間調の彩度(`bellyOf` 彩度 0.55→0.78、`highlightBleach` 0.22→0.16)。
**明るさの総量は増やしていない。**

**残りは翼膜の骨の影のみ。** これは素朴にやると実装できない:

- 膜は `ShapeGeometry`、骨は別のチューブ。**シェーダは骨の位置を知らない**
- `SurfaceSet` は「材質×色」でマテリアルを個体内で共有しているので、
  パーツごとの uniform を足すには `kit.ts` を触る必要がある
- three.js のシャドウマップも使えない(体表は独自 `ShaderMaterial` で
  シャドウのチャンクを取り込んでおらず、`lights: true` 化は全材質の作り直しになる)

使える手がかり: `kit.membrane()` の `ShapeGeometry` は、three.js の既定UVジェネレータにより
**uv にシェイプの (x, y) がそのまま入る**。つまり膜の `uv` は翼ローカル座標そのもの。
頂点シェーダに `varying vec2 vUv;` を足すだけで拾える(ただし hub の位置は不明のまま)。

推奨は**担当ファイル内で完結する案**: 骨の位置を当てにせず、膜自身の層構造で一枚板を壊す。
`#ifdef VEINS` の血管場を、`KEY_DIR` を膜面へ射影した向きへずらしてもう一度評価し、
その分だけ**暗く落とす**(＝血管と筋が自分自身に落とす影)。減算だけなので飽和に効かない。
`TRANSLUCENT` の `thickness` に指の間で垂れる緩い波を重ねると平板さがさらに減る。

**注意**: `membrane` 材質は膜本体だけでなく `ribbedMembrane` の筋のチューブにも使われている。
uv 依存の処理を入れると、そこだけ模様が破綻しないかを必ず見ること。

#### `bellyOf` は「腹の色」ではない(彩度を触る時の注意)

`uBelly` は3役を兼ねている: (a)腹の塗り分け (b)**脇腹の中間調** (c)色ムラの明るい側の混ぜ先。
ここの彩度を下げると**体の側面全体が灰色へ寄る**。
**彩度を触る時は必ず脇腹を見ること。腹単体を見ても異常が出ない。**

## 音(方針は決定済み、実装は未着手)

- 経路確認用の最小例: `tools/audio/smoke.py`

  (純音なら1〜3本なので、ノイズ由来だと数値で確認できている)、
  減衰500ms、ogg 8.1KB

**smoke.py は音の見本ではない**。経路が通るかを確かめただけのもので、
重心6805Hz は打撃音としては明るすぎてシャリついている。流用しないこと。

既存の `src/web/audio/` を全部捨てる必要はない。

- **残すもの**: 音量設定、localStorage への保存、再生の呼び出し口
  (どの場面でどの音を鳴らすか)、`debug.ts` の解析(焼いた音の検品に使える)
- **捨てるもの**: `synth.ts` の波形を作っている部分

`debug.ts` の `bandFlatness` / `tonalPeakRatio` は、
「安っぽさ」を数値で判定するために足したもの。焼いた音の合否判定に使う。
純音・倍音列は少数のビンにエネルギーが集中するので `tonalPeakRatio` が高くなる。

## 触る前に読む罠

### 3Dを外から調べる時

- **`rig.head` には実体が無い。** `finalizeRig()` が静的パーツを `SkinnedMesh` へ統合するため、
  実行時の `rig.head` は geometry を1つも持たない空の Group。
  `new THREE.Box3().setFromObject(rig.head)` は大きさ0の箱を返す。
  **骨の `matrixWorld` から位置だけを取り、距離は全身の高さから割り出すこと。**
  `scratchpad/facecam.sh` がこの正解形(rest 姿勢へ戻してから撮るので待機の揺れも混ざらない)
- **`probe.mjs eval` の中で `import("three")` は解決できない**(bare specifier)。
  `import("/node_modules/.vite/deps/three.js")` を使うこと
- **`probe.mjs shot` の出力先は絶対パスで渡すこと。** harness の cwd はリポジトリ直下なので、
  相対パスだとルートに png が散らばる

### GLSLを書く時

**テンプレートリテラルの中でバッククォートを使うと文字列が途中で閉じる。**
JSDocに `` `feature` `` のように書いてGLSLが壊れた事例がある。
GLSL予約語(`patch` など)の罠は型チェックを素通りするが、こちらは `tsc` が拾う。

### 光と舞台を触る時

床が染まる量は「光の強さ」ではなく**光の向きの縦成分**で決まる。
だからリムライトは弱めるのではなく**寝かせる**のが正解(y 3.4→1.5)。
強さを保ったままキャラの輪郭だけ抜けて、床は染まらない。
中央のプール光は「床を明るくする灯り」ではなく「中央と周辺の差を作る灯り」なので、
差は**周辺を沈める側**(霧・ビネット)で作る。

**色調はライトではなく `CinematicPass` 側で設計する。** ライトで寒暖を割ると
体表シェーダの固定光源とズレてキャラが合成写真のように浮く。

ブルームを上げるなら `threshold` を下げるのではなく `strength` を微増。
しきい値を下げると加算VFXと重なった瞬間に飽和する。

### 押せるかどうかを判定する時

**`.click()` で判定しないこと。** プログラム実行なので、覆われていても成功してしまう。
必ず `elementFromPoint` で見る。ボタンは中心だけでなく上端・下端の3点を見ると、
部分的な潜り込みも拾える。

### エージェントを並行で走らせる時

- 常駐サーバは `HARNESS_VITE_PORT` と `HARNESS_PORT` を必ず指定する。
  自分のポートは `curl -s http://127.0.0.1:<制御ポート>/health` で確かめること
  (起動ログには他系統の番号が混ざることがある)
- 止める時は自分のポートだけ(`lsof -ti :<port> | xargs -r kill`)。
  **`pkill -f harness.mjs` は絶対に打たない**(他系統まで巻き込んで落とした事故がある)
- **作業ツリーは他系統の未コミット編集で汚れる。** 書きかけのファイルがそのまま読み込まれ、
  `TypeError` が連発してアプリが動かなくなることがある。
  **ブラウザ確認が突然壊れたら、まず `git status` で担当外のファイルを見ること。**
  自分の変更のせいだと誤診すると時間を溶かす
- scratchpad は全系統で共有されている。ログや画像のファイル名は自分用に分けること
- **指示書を作る時は必ず最新のコミットを確認すること。** 古い引き継ぎメモから指示を作り、
  既に完了済みの項目を再度指示してしまった事例がある

### 生成サービスと外部ツール

- **生成サービス(ElevenLabs / Suno / Meshy / Tripo など)は使えない。**
  この環境に API キーが無い。キーをもらえれば使える
- PyPI と apt には到達できる(`sudo` も `apt-get` もある)
- **Blender は pip で入る**(`bpy` 5.0.1、GUI無しの Python モジュール版)。
  ブーリアン・ベベル・ディスプレイス・リメッシュが使え、GLB へ書き出せる。
  「丸をつなげた雪だるま」問題への本命の解決策だが、**依頼主が一度見送っている**。
  要望が出たら再提案すること

### 相談中: モッチーの総合値が★4で突出している

## コラボイベントを作った時に分かったこと(2026-09-20 / PR #369)

**mainへはまだ入れていない**(PR #369)。#368(コラボ24体)は
2026-09-20 にマージ済みなので、いまの差分はコラボイベントぶんだけ。

### 相談中: コラボ限定召喚書の光闇の出方

依頼は「全対象モンスターから均等抽選」だが、**属性枠の比率は既存仕様のまま**にした。
12体を完全均等にすると光闇が合計33%出ることになり、既存の★4以上召喚書・
★5召喚書がどれも光闇に低い重みを置いているのと食い違う。
依頼の別の箇所の「**同条件の**コラボキャラクターは完全均等」に合わせてある。

完全均等にする判断が出たら、`COLLAB_SCROLL_TABLES`(`collabGacha.ts`)の
重みを属性ごとに等しくし、`tests/collabGacha.test.ts` の
「同じ属性枠の中では」を全体の均等へ書き換える。

### ミッションの条件は「種類」ではなく「体数」

記念配布は 電気スエゾー1体 + コラボ限定★4以上召喚書1枚。
**書から電気スエゾーが被る目が12分の1ある**ので、「2種類」を条件にすると
その人だけ30個コンプリート不能になる。依頼主の指定で体数へ変えた。
`tests/collabMissions.test.ts` が「条件文に『種類』が残っていないこと」を見張る。

### 配布は2つの仕組みがある。**モンスターはプレゼントボックスだけ**

- `compensation.ts` … ホームの札として**開けば自動で入る。**通貨と召喚書だけ
- `data/gifts.ts` … **プレゼントボックス。**モンスターも配れる。期限を切れる。
  受け取ったものを後から確かめられる

最初 `compensation.ts` へ書いてしまい、プレゼントボックスに出なかった。
**モンスターを配る時・期限を切る時は必ず `gifts.ts`。**

### コラボの判定は `isCollabDexId` だけを通す

`src/data/collabEvent.ts` に集めてある。図鑑IDの前方一致で書くと、
似た名前の種族が増えた時に静かに巻き込む。種族IDで見ること。

### 進捗は「保存」せず「その場で数える」

コラボの所持数・Lv・★・覚醒・編成は、**手持ちを見れば分かる。**
「一度でも達成したか」を保存すると、育てた個体を素材にした時に
進捗が巻き戻って見え、受け取り済みの報酬と食い違う。

数えるしかないもの(勝利数・自動周回数)だけ `collabCampaign` に持つ。
**開催前に積んだぶんは持ち込まない**よう、既存カウンタは開催時点の値を
`baseline` に固定して差分だけを見る。

### 召喚のボタンは、半分の幅に大きな書体を入れない

`summon-cta__btn--ten` は `font-size: 1.18rem` / `min-height: 68px` で
**画面いっぱいの幅を前提にしている。**半分の幅で使うと
「コ ラ ボ 10 連」と1文字ずつ折り返される(実際にそうなった)。
横に2つ並べる時は `summon-cta__pair` と同じ素のボタンにすること。

### 確認用ブラウザの命令は `expression`(`script` ではない)

`tools/harness.mjs` の `eval` は `{ expression }` を受け取る。
`script` を渡すと**`ok: true` が返るのに何も起きない。**
タイトル画面が消えないまま「押せた」と誤解した。
`data-tour="start"` を押した後、`.title-screen` が消えたかを必ず確かめること。

### 召喚画面は「1画面完結」。棚が増えると**祭壇が黙って潰れる**

`.screen.summon-screen` は `height: 100dvh` / `overflow: hidden` で、
`.summon-stage`(魔法陣と宝珠)が余りを吸う `flex: 1`。
**入りきらないと祭壇が0pxまで潰れて、宝珠が上の所持数や見出しへはみ出す。**

実測(390x844・実機ぶんの safe-area を当てた状態):

| 状態 | 祭壇の高さ |
|---|---|
| 通常タブ + 特別召喚書の棚 | **0px** |
| コラボタブ + コラボ限定召喚書の棚 | 36px |

**これは切り替えを入れる前からそうなっている**(棚が出るのは書を持っている人だけ)。
ボタンはどれも押せるままなので巡回では拾えない。
ここの縦を増やす時は、**祭壇に下限を置いて巻物を出す**方へ倒すこと。

### コラボの「もう一度」は、コラボの印で覚える

`SummonMethod` に `COLLAB_CRYSTAL` / `COLLAB_SCROLL` / `COLLAB_SPECIAL` がある。
ここを通常召喚の印(`CRYSTAL`)で書いていたので、
**コラボを引いた直後の「もう一度」が通常召喚になっていた**
(画面はコラボのままで、中身だけが入れ替わる)。

`resolveSummonAgain` の第4引数が開催中かどうか。**終わっていたら通常召喚へ落とす。**
結果画面を開いたまま日付をまたいだ時にここが効く。
配線は `tests/collabSummonUi.test.ts` が本文を読んで見張っている
(押した先が違う関数なので、型では気づけない)。
