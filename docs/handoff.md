# 作業の引き継ぎ

セッションの上限や中断でエージェントが止まった時、**同じ体制をそのまま組み直す**ための覚書。
ここを読めば、途中から同じ品質基準で再開できる。

## 今やっていること

サマナーズウォーと並べて見劣りしない品質へ引き上げる、という目標で
担当を4つに分け、同時に進めている。**担当ファイルは重ならないよう割り当ててある**
(過去に同じファイルを複数のエージェントが触り、作業が混ざる事故を起こしたため)。

| 系統 | 担当ファイル | 常駐サーバのポート |
|---|---|---|
| モンスター | `src/web/three/creature/` 一式、`monsterAvatar.ts` | vite 5350 / 制御 5351 |
| 光と舞台 | `battleStage.ts` の照明・ポストプロセス部分、`postfx/`、`arena.ts` | vite 5320 / 制御 5321 |
| 演出 | `vfx.ts`、`fx/`、`textures.ts` | vite 5330 / 制御 5331 |
| UI | `style.css`、`ui/`、`views/` | vite 5340 / 制御 5341 |

`battleStage.ts` は共有部分があるので、**光と舞台の担当は画作り以外に触らない**
(隊列の配置、当たり判定、回り込み操作、フレーミングの計算には手を入れない)。

## 各系統に出している到達目標

- **モンスター**: 顔(まぶた・眉庇・口・視線)、シルエットの情報量、部位ごとの色分け、
  二次的な動き(尾・耳・布の追従)、星や属性による格の差
- **光と舞台**: 光の方向と質、リムライトでの輪郭の分離、空気遠近、色調の設計、闘技場の情報量
- **演出**: 打撃の重さ(溜め→衝撃→余韻)、属性ごとの質の違い、役割ごとの当たり方、
  回復と支援の見せ場、状態異常が形と動きで読めること
- **UI**: 質感と階層、動き、HPバーの表現。特に戦闘HUD・報酬・一覧・召喚

## 止まった時に、どう再開するか

1. `git log --oneline` で、各系統がどこまでコミットしたかを見る
   (コミット文は日本語で、何をなぜ変えたかが書いてある)
2. 上の表と同じ担当・同じ制約で、新しいエージェントを立てる
3. 「ここまでは終わっている」を伝えたうえで、続きから始めさせる

**失われるのは途中の思考だけで、成果物と方針は残る。**
だから各エージェントには「型チェックが通るたびに、自分の担当ファイルだけを即コミット」
を課している。この規律だけは崩さないこと。

## 全エージェント共通の必須ルール

これは過去の失敗から出た規則なので、必ず引き継ぐこと。

- **型チェックとテストは、CSSとWebGLの安全弁にならない。**
  GLSLのコンパイル失敗も、重なり順の誤りも、`position` の指定漏れも素通りする。
  実際に「モンスターが全員消える」「ステージが押せない」「報酬が受け取れない」を出した。
  必ず `tools/harness.mjs` + `tools/probe.mjs` で実ブラウザから確かめること
  (手順は `docs/battle-stage-notes.md`)
- **撮った画像は必ず自分の目で見る。** 見ずに「できました」と報告しない
- **小さい画像で判断しない。** 「たてがみが消えた」と誤認した失敗がある。
  消えたと思ったら、まず頂点数を測って確かめること
- **加算合成の飽和に注意。** 明るくして目立たせようとしない
- `git add` は担当ファイルだけを明示指定する(`git add -A` と `git add .` は禁止)
- **git push はしない**(取りまとめ役がまとめて行う)
- ブランチ `claude/turn-based-battle-game-ioqjai` から動かない

## 中断した系統の再開メモ

### 光と舞台(未着手。調査だけ済み)

**前回の黒画面はポストプロセスのせいではない。** 退避ブランチ `wip/aaa-interrupted` の
差分を取ると `postfx/` は1行も変わっておらず、`battleStage.ts` も霧の1行だけだった。
実際に消えていたのは `src/web/style.css` の853行全部で、
`.battle-stage` の寸法指定が失われたためキャンバスが8031pxに崩れたと見られる。
**あの退避ブランチは1系統の作業ではなく、中断時点の作業ツリー全体のスナップショット。**

現状の `setupLights()` はキー/フィル/リム/逆リム/中央プールの5灯で、方向と質はすでに良い。
足りないのは次の3点:

- **色調が青紫一色**。ライトではなく `CinematicPass` の `uShadowTint` / `uHighlightTint` /
  `uTintStrength` で寒暖の割りを設計し直す方が安全。ライト側を触ると
  体表シェーダの固定光源とのズレが出る
- **接地感**。足元の暗さが浅い。`HemisphereLight` か `scene.environmentIntensity` を下げる方向
- **ブルームが控えめすぎる**。上げるなら `threshold` を下げるのではなく `strength` を微増
  (0.18 → 0.24 程度)。しきい値を下げると加算VFXと重なった瞬間に飽和する

`wip/aaa-interrupted` の `arena.ts` の差分(+179行)は筋が良いが未検証。取り込むなら
(a)空の天体 (b)観客席を7段へ (c)観客と手持ちの灯り (d)遠景の尖塔、の4つに割って
1つずつ検証すること。特に(c)は加算の点が遠景に散るのでブルームとの相性を必ず見る。

`battleStage.ts` の霧を `FogExp2(0x2a3055, 0.0165)` → `(0x2f3660, 0.0235)` に濃くする案は
1行で効果が大きい。体表シェーダは fog を組み込んでいないため、濃くしても
手前のキャラは白まず闘技場だけが奥へ退く。

### 戦闘演出(未着手。調査だけ済み)

**コードに書いてある大きさの値は、そのままでは効いていない。** これを知らずに数値を
いじると時間を溶かすので、先に読むこと。

- 板1枚の最大は「画面の高さの16%」で頭打ち。実測で約1.63ワールド単位。
  つまり `endScale: 6.5` のような指定は切り捨てられ、**衝撃波の輪は指定の1/3の大きさでしか出ていない**
- 板の濃さには一律 0.42 が掛かる。これ以上薄くする方向の調整は意味が薄い
- **同時生存の上限が厳しい**。板は6枚で間引きが始まり、14枚で強制置換。帯は8枚。
  **同時に多くを出す設計は成立しない。** 多段化するなら「同時に増やす」のではなく
  時間的にずらして総数を保つこと

この制約は「派手さは明るさではなく間・形・timing で作る」という方針と技術的に一致する。

着手順の案(前任者の調査による):

1. `6976a3e` が足したテクスチャ7枚(`impactStar` / `crackDecal` / `rippleRings` /
   `godRay` / `voidCore` / `chevron` / `hexPanel`)が**1枚も接続されていない**。まずこれを繋ぐ
2. **打撃の三段化**。今は閃光・光球・輪が全部同時に発火して「一点集中」が無い。
   溜め → 衝撃(角のある形を極短命で) → 余韻(地面の亀裂を1.2秒残す)。
   跡は光ではないので、**加算の飽和を増やさずに時間を稼げる唯一の手札**
3. **大きい輪は板ではなく帯で描く**。線なので加算面積が増えず、安全に大きく鋭い輪が出せる。
   `6976a3e` が足した `grow` はこのためのものだが、まだ誰も使っていない
4. **属性差は色ではなく間で**。炎は3波を段階的にずらす、雷は溜めゼロで一撃、
   水は地面の波紋を時間差、光は上へ抜ける、闇は **NormalBlending** で背景を食う
   (周囲の加算光が締まって見えるので、明るくせずに強く見せられる)
5. `blunt`(打撃)が未実装。今は斬撃と刺突しか分岐が無い

**共通パラメータを上げる前に、上記3をやりきること。** それでも足りない場合、
上げるべきは板の大きさの上限ではなく**同時生存数の上限**の方(飽和の主因は
1枚の大きさより枚数のため)。

サンドボックスが速い。`probe.mjs eval` から
`import('/src/web/three/fx/vfxSandbox.ts').then(m=>m.mountVfxSandbox({set:'impact'}))`
で戦闘の進行を待たずに全エフェクトを並べられる。`freezeAt` で同じ瞬間を再現できるので、
変更前後の比較はこれを使うこと。

### UI(未着手。調査と健全性確認だけ済み)

本線は健全。縦横ともキャンバスの寸法は画面ぴったりで、ステージ札も
戦闘中のボタンも最前面。前任者が残した8031pxの崩れは本線には入っていない。

着手順の案:

1. `wip/aaa-interrupted` の `ui/battleHud.css` から**使える部分だけを選別**する。
   あのブランチは `style.css` から853行を切り出して新ファイルへ移す大手術で、
   崩れの原因はほぼ移設中の高さ指定。**丸ごと取り込まないこと。**
   HPバー・状態異常バッジ・スキルドックの「見た目だけ」を1ブロックずつ現行 `style.css` へ移し、
   1ブロックごとに縦横のキャンバス高さを測って即コミットする。**ファイル分割は後回し**
2. **HUDの重なり回避を、質感より先にやる**。味方4体+敵4体のHPバーが中央で
   団子になって重なり、名前が全部途中で切れている。奥の列を小さく・薄くするか、
   列ごとに縦のオフセットを変える
3. HPバーの表現(削れた分を追う残像、シールドの重ね帯、回復の走り、危険域の脈動、被弾の横揺れ)
4. 報酬画面 → 一覧・図鑑・編成 → 召喚

**未確認の1点(再開時に最初に確かめること)**: 横画面 900x430 のステージ詳細で、
「挑戦する」ボタンの中心が下部ナビに覆われているという測定結果が1度出た。
`.screen` に下余白があるのでスクロールすれば届くはずで、押せない不具合ではなく
「初期表示でボタンがナビの下に潜る」使い勝手の粗さと見られるが、未再現。縦画面では出ない。

### 常駐サーバの注意

- 複数の系統が同時に起動するので、`HARNESS_VITE_PORT` と `HARNESS_PORT` を必ず指定する。
  自分のポートは `curl -s http://127.0.0.1:<制御ポート>/health` で確かめること
  (起動ログには他系統の番号が混ざることがある)
- 止める時は `kill -9`。普通の `kill` では vite だけ落ちて制御ポートが残り、
  中途半端に壊れた状態になる
- **`pkill -f harness.mjs` は絶対に打たないこと。**
  並行作業中の他系統の常駐サーバまで巻き込んで落とす(実際にやらかした事故がある)。
  自分の分だけを止めるには、環境変数からPIDを特定すること:

```
for p in $(ps aux | grep "[h]arness.mjs" | awk '{print $2}'); do
  echo "PID=$p $(tr '\0' '\n' < /proc/$p/environ | grep '^HARNESS_PORT=')"
done
```

### 並行作業中に踏みやすい罠

- **作業ツリーは他系統の未コミット編集で汚れる。** 書きかけのファイルが
  そのまま読み込まれ、`TypeError` が連発してアプリが動かなくなることがある。
  **ブラウザ確認が突然壊れたら、まず `git status` で担当外のファイルが
  変わっていないかを見ること。** 自分の変更のせいだと誤診すると時間を溶かす
- scratchpad は全系統で共有されている。ログや画像のファイル名は自分用に分けること
- **押せるかどうかを `.click()` で判定しないこと。** プログラム実行なので、
  覆われていても成功してしまう。必ず `elementFromPoint` で見ること。
  ボタンは中心だけでなく上端・下端の3点を見ると、部分的な潜り込みも拾える

## 品質の判定

各系統が上がったら、**別の批評役**に評価させる。
「サマナーズウォーと並べて、どちらが上等に見えるか」を厳しく問い、
勝てていなければ何が足りないかを言葉にさせ、担当へ差し戻してもう一周する。

判定の芯は `docs/design-concept.md`(ゲームの面白さの芯)と
`docs/battle-stage-notes.md`(描画の前提と落とし穴)に置く。

### 体表の質感(1巡目完了。残りの課題)

参考画像に寄せる方向で7点を入れた(暗部を青く明部を白く / 鱗に縁 /
結晶を内側から光らせる / 金属の濡れたハイライトと継ぎ目 / 遠くで線の模様を消す /
発光部を中心だけ白熱 / 布に襞)。**明るさの総量は増やしていない。**

残っている課題(前任者の申し送り、優先順):

1. **中間調の彩度が抜け気味。** 水ドラゴンの脇腹が青灰色になる。
   `bellyOf` の彩度0.55倍と `highlightBleach` が重なって明部が灰白へ寄っている。
   腹の彩度を残すか、bleach を 0.22 → 0.16 へ落とすのが次の一手
2. **毛皮に房の縁が無い。** 鱗でやったのと同じ処理(輪郭に溝と稜)を
   `strandPattern` にも入れる余地がある
3. **翼膜がまだ紙寄り。** 骨の影が膜に落ちる表現が無いので一枚板に見える
4. `detailFade` の閾値(鱗 0.062 / 継ぎ目 0.030)は目分量。実機で追い込む余地
5. **床のプール光と背後のピンクが強く、寄ると局所色を食う**(光と舞台の担当領域)。
   体表側でリムを細めて緩和したが、根本はライト側

### GLSLを書く時の罠(もう1つ)

**テンプレートリテラルの中でバッククォートを使うと文字列が途中で閉じる。**
JSDocに `` `feature` `` のように書いてGLSLが壊れた事例がある。
GLSL予約語(`patch` など)の罠は型チェックを素通りするが、こちらは `tsc` が拾う。

### 頭部の作り直し(未着手。調査完了・手順まで確定)

**`addBeastHead` の影響範囲は竜と狼の2体だけ。** グリフォンは `buildGriffon` が頭を自前に組むので無関係。
アタッカー/ボス/デバッファーの役割ビルダー内の `addBeastHead` は、現13種が全員
専用骨格を持つため**どこからも呼ばれていない**。切り替えの検証は
`roster=wolf:DARK|dragon:FIRE` の1枚で足りる。

手順(そのまま実行できる形):

1. `BeastHeadOptions` に `hard?: boolean` を足す(`addTail` の `o: { hard?: boolean }` と同じ流儀)
2. `hard` のとき、`kit.ball` で組んでいる次を差し替える。
   **球を hull に置き換えるだけでなく、個数を減らして1本の連続した立体にすることが要点**
   - 頭蓋(roles.ts の球4〜5個)→ `kit.hull()` 1本。`sides: 7`、眉庇で `keel` を効かせて眉間の稜線を出す
   - 頬骨・眉庇(`lens` と `addFaceEyes` の brow)→ `kit.plate()`。`wrap` を頭蓋の横半径に
   - 下顎(`ball` 2個)→ `kit.hull()` 1本の角柱。咬筋は `plate`
3. `hard` が false のときは**現行コードをそのまま通す**。狼が角張らないことを画で確認
4. `hard: true` を立てるのは `buildDragon` / `buildBoss` / `buildDebuffer` / `buildAttacker`。
   **`buildWolf` は false のまま**

続けて: 顔の表情(`addFaceEyes` も全種別共有なので切り替え引数が要る)、
竜の胸の前端に `plateStack` を1本、`plate()` の頂点削減(1枚108頂点。手組みで約半分)。

### 3Dを外から調べる時の罠

- **`rig.head` には実体が無い。** `finalizeRig()` が静的パーツを `SkinnedMesh` へ統合するため、
  実行時の `rig.head` は geometry を1つも持たない空の Group。
  `new THREE.Box3().setFromObject(rig.head)` は大きさ0の箱を返す。
  **骨の `matrixWorld` から位置だけを取り、距離は全身の高さから割り出すこと。**
  `scratchpad/facecam.sh` がこの正解形(rest 姿勢へ戻してから撮るので待機の揺れも混ざらない)
- **`probe.mjs eval` の中で `import("three")` は解決できない**(bare specifier)。
  `import("/node_modules/.vite/deps/three.js")` を使うこと
- **`probe.mjs shot` の出力先は絶対パスで渡すこと。** harness の cwd はリポジトリ直下なので、
  相対パスだとルートに png が散らばる

### 体表の質感(2巡目完了。残りは翼膜の骨の影だけ)

**指示書を作る時は必ず最新のコミットを確認すること。** 古い引き継ぎメモから指示を作り、
既に完了済みの項目を再度指示してしまった事例がある(担当が事実確認に切り替えて回避)。

完了済み: 毛皮の房の縁 / 中間調の彩度(`bellyOf` 彩度 0.55→0.78、`highlightBleach` 0.22→0.16)/
床のプール光と背後のピンク / 色調 / 霧 / ブルーム。
**残りは翼膜の骨の影のみ。**

#### `bellyOf` は「腹の色」ではない(彩度を触る時の注意)

`uBelly` は3役を兼ねている: (a)腹の塗り分け (b)**脇腹の中間調** (c)色ムラの明るい側の混ぜ先。
ここの彩度を下げると**体の側面全体が灰色へ寄る**。
**彩度を触る時は必ず脇腹を見ること。腹単体を見ても異常が出ない。**

#### 床が染まる量は「光の強さ」ではなく「光の向きの縦成分」で決まる

だからリムライトは弱めるのではなく**寝かせる**のが正解(y 3.4→1.5)。
強さを保ったままキャラの輪郭だけ抜けて、床は染まらない。
中央のプール光は「床を明るくする灯り」ではなく「中央と周辺の差を作る灯り」なので、
差は**周辺を沈める側**(霧・ビネット)で作る。
色調はライトではなく `CinematicPass` 側で設計する(ライトで寒暖を割ると
体表シェーダの固定光源とズレてキャラが合成写真のように浮く)。

#### 翼膜の骨の影は、素朴にやると実装できない

- 膜は `ShapeGeometry`、骨は別のチューブ。**シェーダは骨の位置を知らない**
- `SurfaceSet` は「材質×色」でマテリアルを個体内で共有しているので、
  パーツごとの uniform を足すには `kit.ts` を触る必要がある
- three.js のシャドウマップも使えない(体表は独自 `ShaderMaterial` で
  シャドウのチャンクを取り込んでおらず、`lights: true` 化は全材質の作り直しになる)

使える手がかり: `kit.membrane()` の `ShapeGeometry` は、three.js の既定UVジェネレータにより
**uv にシェイプの (x, y) がそのまま入る**。つまり膜の `uv` は翼ローカル座標そのもの。
頂点シェーダに `varying vec2 vUv;` を足すだけで拾える(ただし hub の位置は不明のまま)。

推奨は**担当ファイル内で完結する案**: 骨の位置を当てにせず、膜自身の層構造で一枚板を壊す。
`#ifdef VEINS` の血管場を、`KEY_DIR` を膜面へ射影した向きへずらしてもう一度評価し、
その分だけ**暗く落とす**(＝血管と筋が自分自身に落とす影)。減算だけなので飽和に効かない。
`TRANSLUCENT` の `thickness` に指の間で垂れる緩い波を重ねると平板さがさらに減る。

**注意**: `membrane` 材質は膜本体だけでなく `ribbedMembrane` の筋のチューブにも使われている。
uv 依存の処理を入れると、そこだけ模様が破綻しないかを必ず見ること。

## 中断時点(制限直前)の状態と、再開時にやること

### 決まったこと: 音は「事前に焼く」方式へ変える

依頼主の判断で、**Web Audio API でのリアルタイム合成をやめ、
事前に音声ファイルへ焼き込む方式へ切り替える**。

理由は、ブラウザ上で毎回計算する都合上どうしても処理が簡素になり
(特にリバーブ)、それが「安っぽさ」の主因だと判断したため。
事前に焼くなら重い処理を好きなだけかけられる。

**「サンプルファイルを使わない」という縛りは依頼主の指示ではなく、
こちらが勝手に設けたものだった**。焼く方が良くなるならそちらを取る。

道具はすでに入れて、動作確認まで済んでいる。

- 仮想環境: `tools/audio/.venv`(`.gitignore` 済み)
- numpy 2.4.6 / scipy 1.17.1 / soundfile 0.14.0 / pedalboard 0.9.24
- 書き出せる形式: WAV / OGG / FLAC / MP3
- 経路確認用の最小例: `tools/audio/smoke.py`
  実測: ピーク2488Hz、重心6805Hz、ピーク付近のビン数113
  (純音なら1〜3本なので、ノイズ由来だと数値で確認できている)、
  減衰500ms、ogg 8.1KB

**smoke.py は音の見本ではない**。経路が通るかを確かめただけのもので、
重心6805Hz は打撃音としては明るすぎてシャリついている。流用しないこと。

既存の `src/web/audio/` を全部捨てる必要はない。

- **残すもの**: 音量設定、localStorage への保存、再生の呼び出し口
  (どの場面でどの音を鳴らすか)、`debug.ts` の解析(焼いた音の検品に使える)
- **捨てるもの**: `synth.ts` の波形を作っている部分

`debug.ts` の `bandFlatness` / `tonalPeakRatio` は、
「安っぽさ」を数値で判定するために足したもの。焼いた音の合否判定に使う。
純音・倍音列は少数のビンにエネルギーが集中するので `tonalPeakRatio` が高くなる。

### 外部ツールについて調べた結果

- **生成サービス(ElevenLabs / Suno / Meshy / Tripo など)は使えない。**
  この環境に API キーが無い。キーをもらえれば使える
- PyPI と apt には到達できる(`sudo` も `apt-get` もある)
- **Blender は pip で入る**(`bpy` 5.0.1、GUI無しの Python モジュール版)。
  ブーリアン・ベベル・ディスプレイス・リメッシュが使え、GLB へ書き出せる。
  「丸をつなげた雪だるま」問題への本命の解決策だが、
  **今回は依頼主が見送った**(音を先にやる)。要望が出たら再提案すること

### やりかけで止まっていること

1. **トレントの枝が効いていない(要修正)**
   画面で確認したところ、ゴーレムとほぼ同じに見える。
   枝(`TEMPLATE_TRAITS.treant`)が体に埋もれている。原因は2つ:
   - ディフェンダーの骨格は頭が低く、左右に巨大な肩の岩塊がある。
     枝を `rig.head` の y=0.16 から生やしても肩の線を越えられない
   - 葉叢に `p.accent` を使っているが、体色と差が付かず「体のこぶ」に見える

   直し方: 枝をもっと長く・細くし、肩の線より明確に上へ出す。
   葉叢は枝の先端に付ける(頭の周りではなく)。色は体色から離す。
   確認は `roster=treant:GRASS,treant:WATER|golem:GRASS,golem:WATER` で
   ゴーレムと並べて見ること。**小さい画像で判断しない**

2. **スキル演出**: `vfx.ts` / `fx/strips.ts` は型チェックが通る状態で保全済み。
   未着手として残っているのは、使われていないテクスチャ7枚の接続、
   3段構えの着弾、大きな環をビルボードではなく帯で描くこと、
   属性の differentiation を色ではなく間で付けること、`blunt` の実装
