## クラウド保存の競合(2026-09-25。#415 の続き)

端末とクラウドの内容が分かれると `save` は STALE_REVISION で止まる(古い方で上書きしないため)。
#415 までは止まったままで、本人が「保存内容を確認して再開」を押すまで端末の遊びがクラウドに届かなかった。

- **いまは止まらない。**内容が分かれたら、端末の最新データを `save_copy` で
  `crimon_recovery_conflict_copies`(端末ごとに1行、`account_id`+`device_id`)へ控える
- 本来のバックアップ(`latest_save`)・世代・アリーナの行には**触らない**。
  端末側も `revision` と `lastUploadedSave` を進めない(進めると次の自動保存が別端末の続きを上書きする)
- 競合中の自動保存は `load` → 同じ内容なら解消 / 違えば控えを更新(内容が同じなら送らない)
- 表は `supabase/migrations/20260925150000_recovery_conflict_copies.sql`。
  `recovery-edge.yml` が DB → deploy の順で流す(表が無いまま API を配ると控えが500になる)
- **管理画面は、いちばん新しい方を出す。**`crimon-admin` が控えを読み、控えの方が新しければ
  行の値・日時を控えから出す(`newestSource: "COPY"`)。本来のバックアップと控えは行の下に並べて比べられる。
  控えの表を読めない時は `conflictCopyStatus: "unavailable"` で画面に警告を出す(黙って古い方だけを出さない)
- **開いた時に揃える(`syncOnOpen`)。**依頼主「ログインした時点でそのアカウントに合わせるだけではだめなんですか？」。
  前は端末が「上げる」だけで「取りに行く」をしなかったのが、分かれる元だった。
  起動時と画面へ戻った時(60秒に1回まで)に `load` し、`decideOpenSync` で決める:
  - 他の端末が保存していない(世代が同じ) → 何もしない
  - この端末で最後に上げた後遊んでいない → **クラウドに合わせて読み直す**(クラウドには書かない)
  - 両方で遊んだ → **後で遊んだ方**へ揃える。端末側の時刻は `savePlayerState` が書く
    `crimon_save_touched_at_v1`、無い古い端末は `conflictCopySavedAt`、それも無ければクラウドに合わせる
  - 負けた方は必ずクラウドに残す。端末が負けたら `save_copy`(端末の行)、
    クラウドが負けたら `save_copy`(`device_id = "replaced-main"`)に置いてから本来の方を更新する。
    **控えが書けなければ合わせない**
  - 端末が負けた時は、本来のバックアップを**同じ内容で保存し直す**。控えは「いま」の日時で入るので、
    そうしないと管理画面で負けた方が最新に見える
- **起動直後は「このページが書く前」の姿で判断する**(`startupSaveSnapshot`)。経験ピッグ・お知らせ・
  ログインボーナスで開いた瞬間にセーブが変わるので、それを「遊んだ」と数えると開いただけの端末が勝つ
- 読み直しは `restoreCloudSave` + `cloudRestoreNavigationGuard.ts` の退避鍵を使う
  (直前の端末データは「クラウド復旧前の端末データへ戻す」で戻せる)
- 管理画面は、控えが本来の方より新しい時だけ「⚠ 保存が分かれています」を出す(揃った後も控えは残るため)
- 実画面の検査は `tools/recoveryPreview.mts`(HOME撮影のCIで回る。手元では `CRIMON_CHROMIUM=/opt/pw-browsers/chromium`)

## スタミナポーション(一巡終わっている。決めた理由だけ残す)

`#352`〜`#356` で入れた。**作り直す前にここを読むこと。**
「なぜそうしたか」は理由ごと決めてあるので、知らずに戻すと同じ議論をやり直す。

### 置き場所

- **ダイヤショップには置かない。**ダイヤ → スタミナ → 周回 → ダイヤ の輪ができて、
  スタミナという仕組みそのものが消える(`src/data/crystalShop.ts` に元からある指定)
- 売るのは**ゴールドの棚(毎時入れ替わり)**。並ぶ数は 1 / 3 / 5 で、
  まとめて並ぶ時ほど1個あたりが安い。**才能覚醒の素材とは別の枠(role 0)**を使う
  (同じ枠だと、片方が並ぶ時間帯はもう片方が必ず消える)
- **棚は両側で決まる。**クライアントだけ変えると「その商品はありません」、
  サーバだけだと「買えたのに増えない」。流し終えたマイグレーションは二度と走らないので、
  商品を足す時は必ず新しいファイル。`tests/arenaConfigParity.test.ts` が突き合わせる

### 配る量

日次3 / 週次10 / 月次30。どれも「スタミナを消費する」の1本に集める
(複数へ散らすと、1日に受け取れる量が読めなくなる)。
**周期が長いほど1回の取り分を大きくする。**週10に対して月3のままにしていて、
月末に受け取る意味が無くなっていた。

ポーションは上限を超えて持てるので、**日次で配っても満タンの人が捨てずに済む**
(`stamina` を日次で配ると捨てることになる)。

### 自動周回での使い方

- 上限は**数**で持つ(`staminaPotionFarmBudget`。0 = 使わない)。
  最初は入 / 切だったが、**入にすると持っている分を使い切るまで止まらず**、
  貯めたい人は周回のたびに切り替えるしかなかった
- **「全部」は所持数ではなく印**(`STAMINA_POTION_UNLIMITED_BUDGET`)で持つ。
  所持数を焼き付けると、周回中に増えたぶんが使われない
- **ダイヤは絶対に自動で使わない。**尽きたら `STAMINA` で正常に終わる
- 「最大 ×◯回」も決めた数だけを数える

### 0個で隠したら「壊れている」と読まれた

ホームの所持数を、幅の節約のつもりで「持っている時だけ出す」にしていた。
依頼主が0個の画面を見て**「ポーションがみえません」**と言った。
**無いから出ていないのか、出す作りになっていないのか、画面から区別できない。**
数を出す目的そのものを外していた。いまは0個でも出し、色を落としている。

**数を見せる欄は、0でも出すこと。**消してよいのは「その機能自体がまだ無い」時だけ。

### まだ相談していないこと

**アリーナショップの週2個**が、いまの配布量(日次3・週次10・月次30)に対して
意味が薄い。整理するか残すかは未決。依頼主に聞くこと。

## 自動周回(一巡終わっている。決めた理由だけ残す)

- **1周の時間は実測の中央値そのまま。**倍率で割り戻さない。x8で3秒なら3秒/周。
  以前あった「最低30〜45秒」は、**速く倒せる編成を組んでも周回が速くならない**
  原因だったので外した。残っている1秒は速さの調整ではなく**暴走止め**
  (0秒だと「経過時間 ÷ 1周」が跳ね、復帰した瞬間に数万回ぶんの処理権が生まれる)
- **周回中でも他の戦闘へ入れる。**スタミナの取り合いは起きない——
  既存実装が1周ごとに最新の控えを見てから次の1戦を始める作りで、前払いをしていない
- 報酬は**正式なクリア報酬処理**を通す。簡易テーブルを作らない

## 戦闘演出(未着手。調査だけ済み)

**コードに書いてある大きさの値は、そのままでは効いていない。** これを知らずに数値を
いじると時間を溶かすので、先に読むこと。

- 板1枚の最大は「画面の高さの16%」で頭打ち。実測で約1.63ワールド単位。
  つまり `endScale: 6.5` のような指定は切り捨てられ、**衝撃波の輪は指定の1/3の大きさでしか出ていない**
- 板の濃さには一律 0.42 が掛かる。これ以上薄くする方向の調整は意味が薄い
- **同時生存の上限が厳しい**。板は6枚で間引きが始まり、14枚で強制置換。帯は8枚。
  **同時に多くを出す設計は成立しない。** 多段化するなら「同時に増やす」のではなく
  時間的にずらして総数を保つこと

この制約は「派手さは明るさではなく間・形・timing で作る」という方針と技術的に一致する。

着手順の案:

1. `6976a3e` が足したテクスチャ7枚(`impactStar` / `crackDecal` / `rippleRings` /
   `godRay` / `voidCore` / `chevron` / `hexPanel`)が**1枚も接続されていない**。まずこれを繋ぐ
2. **打撃の三段化**。今は閃光・光球・輪が全部同時に発火して「一点集中」が無い。
   溜め → 衝撃(角のある形を極短命で) → 余韻(地面の亀裂を1.2秒残す)。
   跡は光ではないので、**加算の飽和を増やさずに時間を稼げる唯一の手札**
3. **大きい輪は板ではなく帯で描く**。線なので加算面積が増えず、安全に大きく鋭い輪が出せる。
   `6976a3e` が足した `grow` はこのためのものだが、まだ誰も使っていない
4. **属性差は色ではなく間で**。炎は3波を段階的にずらす、雷は溜めゼロで一撃、
   水は地面の波紋を時間差、光は上へ抜ける、闇は **NormalBlending** で背景を食う
   (周囲の加算光が締まって見えるので、明るくせずに強く見せられる)
5. `blunt`(打撃)が未実装。今は斬撃と刺突しか分岐が無い

**共通パラメータを上げる前に、上記3をやりきること。** それでも足りない場合、
上げるべきは板の大きさの上限ではなく**同時生存数の上限**の方(飽和の主因は
1枚の大きさより枚数のため)。

サンドボックスが速い。`probe.mjs eval` から
`import('/src/web/three/fx/vfxSandbox.ts').then(m=>m.mountVfxSandbox({set:'impact'}))`
で戦闘の進行を待たずに全エフェクトを並べられる。`freezeAt` で同じ瞬間を再現できるので、
変更前後の比較はこれを使うこと。

## モンスターの造形

### 頭部の作り直し(未着手。調査完了・手順まで確定)

**`addBeastHead` の影響範囲は竜と狼の2体だけ。** グリフォンは `buildGriffon` が頭を自前に組むので無関係。
アタッカー/ボス/デバッファーの役割ビルダー内の `addBeastHead` は、現13種が全員
専用骨格を持つため**どこからも呼ばれていない**。切り替えの検証は
`roster=wolf:DARK|dragon:FIRE` の1枚で足りる。

手順(そのまま実行できる形):

1. `BeastHeadOptions` に `hard?: boolean` を足す(`addTail` の `o: { hard?: boolean }` と同じ流儀)
2. `hard` のとき、`kit.ball` で組んでいる次を差し替える。
   **球を hull に置き換えるだけでなく、個数を減らして1本の連続した立体にすることが要点**
   - 頭蓋(roles.ts の球4〜5個)→ `kit.hull()` 1本。`sides: 7`、眉庇で `keel` を効かせて眉間の稜線を出す
   - 頬骨・眉庇(`lens` と `addFaceEyes` の brow)→ `kit.plate()`。`wrap` を頭蓋の横半径に
   - 下顎(`ball` 2個)→ `kit.hull()` 1本の角柱。咬筋は `plate`
3. `hard` が false のときは**現行コードをそのまま通す**。狼が角張らないことを画で確認
4. `hard: true` を立てるのは `buildDragon` / `buildBoss` / `buildDebuffer` / `buildAttacker`。
   **`buildWolf` は false のまま**

続けて: 顔の表情(`addFaceEyes` も全種別共有なので切り替え引数が要る)、
竜の胸の前端に `plateStack` を1本、`plate()` の頂点削減(1枚108頂点。手組みで約半分)。

**部品数を減らす作業は、描画回数を減らす作業と同じ方向を向いている。**
上の「球を減らして1本の立体にする」は造形と性能の両方に効くので、
性能を先にやるつもりでも、入口はここになる。

### トレントの枝が効いていない(要修正)

画面で確認したところ、ゴーレムとほぼ同じに見える。枝(`TEMPLATE_TRAITS.treant`)が
体に埋もれている。原因は2つ:

- ディフェンダーの骨格は頭が低く、左右に巨大な肩の岩塊がある。
  枝を `rig.head` の y=0.16 から生やしても肩の線を越えられない
- 葉叢に `p.accent` を使っているが、体色と差が付かず「体のこぶ」に見える

直し方: 枝をもっと長く・細くし、肩の線より明確に上へ出す。
葉叢は枝の先端に付ける(頭の周りではなく)。色は体色から離す。
確認は `roster=treant:GRASS,treant:WATER|golem:GRASS,golem:WATER` で
ゴーレムと並べて見ること。**小さい画像で判断しない**

### 体表の質感(2巡目完了。残りは翼膜の骨の影だけ)

完了済み: 暗部を青く明部を白く / 鱗に縁 / 結晶を内側から光らせる /
金属の濡れたハイライトと継ぎ目 / 遠くで線の模様を消す / 発光部を中心だけ白熱 /
布に襞 / 毛皮の房の縁 / 中間調の彩度(`bellyOf` 彩度 0.55→0.78、`highlightBleach` 0.22→0.16)。
**明るさの総量は増やしていない。**

**残りは翼膜の骨の影のみ。** これは素朴にやると実装できない:

- 膜は `ShapeGeometry`、骨は別のチューブ。**シェーダは骨の位置を知らない**
- `SurfaceSet` は「材質×色」でマテリアルを個体内で共有しているので、
  パーツごとの uniform を足すには `kit.ts` を触る必要がある
- three.js のシャドウマップも使えない(体表は独自 `ShaderMaterial` で
  シャドウのチャンクを取り込んでおらず、`lights: true` 化は全材質の作り直しになる)

使える手がかり: `kit.membrane()` の `ShapeGeometry` は、three.js の既定UVジェネレータにより
**uv にシェイプの (x, y) がそのまま入る**。つまり膜の `uv` は翼ローカル座標そのもの。
頂点シェーダに `varying vec2 vUv;` を足すだけで拾える(ただし hub の位置は不明のまま)。

推奨は**担当ファイル内で完結する案**: 骨の位置を当てにせず、膜自身の層構造で一枚板を壊す。
`#ifdef VEINS` の血管場を、`KEY_DIR` を膜面へ射影した向きへずらしてもう一度評価し、
その分だけ**暗く落とす**(＝血管と筋が自分自身に落とす影)。減算だけなので飽和に効かない。
`TRANSLUCENT` の `thickness` に指の間で垂れる緩い波を重ねると平板さがさらに減る。

**注意**: `membrane` 材質は膜本体だけでなく `ribbedMembrane` の筋のチューブにも使われている。
uv 依存の処理を入れると、そこだけ模様が破綻しないかを必ず見ること。

#### `bellyOf` は「腹の色」ではない(彩度を触る時の注意)

`uBelly` は3役を兼ねている: (a)腹の塗り分け (b)**脇腹の中間調** (c)色ムラの明るい側の混ぜ先。
ここの彩度を下げると**体の側面全体が灰色へ寄る**。
**彩度を触る時は必ず脇腹を見ること。腹単体を見ても異常が出ない。**

## 音(方針は決定済み、実装は未着手)

依頼主の判断で、**Web Audio API でのリアルタイム合成をやめ、

理由は、ブラウザ上で毎回計算する都合上どうしても処理が簡素になり
(特にリバーブ)、それが「安っぽさ」の主因だと判断したため。
事前に焼くなら重い処理を好きなだけかけられる。

**「サンプルファイルを使わない」という縛りは依頼主の指示ではなく、
こちらが勝手に設けたものだった**。焼く方が良くなるならそちらを取る。

道具はすでに入れて、動作確認まで済んでいる。

- 仮想環境: `tools/audio/.venv`(`.gitignore` 済み)
- numpy 2.4.6 / scipy 1.17.1 / soundfile 0.14.0 / pedalboard 0.9.24
- 書き出せる形式: WAV / OGG / FLAC / MP3
- 経路確認用の最小例: `tools/audio/smoke.py`
  実測: ピーク2488Hz、重心6805Hz、ピーク付近のビン数113
  (純音なら1〜3本なので、ノイズ由来だと数値で確認できている)、
  減衰500ms、ogg 8.1KB

**smoke.py は音の見本ではない**。経路が通るかを確かめただけのもので、
重心6805Hz は打撃音としては明るすぎてシャリついている。流用しないこと。

既存の `src/web/audio/` を全部捨てる必要はない。

- **残すもの**: 音量設定、localStorage への保存、再生の呼び出し口
  (どの場面でどの音を鳴らすか)、`debug.ts` の解析(焼いた音の検品に使える)
- **捨てるもの**: `synth.ts` の波形を作っている部分

`debug.ts` の `bandFlatness` / `tonalPeakRatio` は、
「安っぽさ」を数値で判定するために足したもの。焼いた音の合否判定に使う。
純音・倍音列は少数のビンにエネルギーが集中するので `tonalPeakRatio` が高くなる。

## 触る前に読む罠

### 3Dを外から調べる時

- **`rig.head` には実体が無い。** `finalizeRig()` が静的パーツを `SkinnedMesh` へ統合するため、
  実行時の `rig.head` は geometry を1つも持たない空の Group。
  `new THREE.Box3().setFromObject(rig.head)` は大きさ0の箱を返す。
  **骨の `matrixWorld` から位置だけを取り、距離は全身の高さから割り出すこと。**
  `scratchpad/facecam.sh` がこの正解形(rest 姿勢へ戻してから撮るので待機の揺れも混ざらない)
- **`probe.mjs eval` の中で `import("three")` は解決できない**(bare specifier)。
  `import("/node_modules/.vite/deps/three.js")` を使うこと
- **`probe.mjs shot` の出力先は絶対パスで渡すこと。** harness の cwd はリポジトリ直下なので、
  相対パスだとルートに png が散らばる

### GLSLを書く時

**テンプレートリテラルの中でバッククォートを使うと文字列が途中で閉じる。**
JSDocに `` `feature` `` のように書いてGLSLが壊れた事例がある。
GLSL予約語(`patch` など)の罠は型チェックを素通りするが、こちらは `tsc` が拾う。

### 光と舞台を触る時

床が染まる量は「光の強さ」ではなく**光の向きの縦成分**で決まる。
だからリムライトは弱めるのではなく**寝かせる**のが正解(y 3.4→1.5)。
強さを保ったままキャラの輪郭だけ抜けて、床は染まらない。
中央のプール光は「床を明るくする灯り」ではなく「中央と周辺の差を作る灯り」なので、
差は**周辺を沈める側**(霧・ビネット)で作る。

**色調はライトではなく `CinematicPass` 側で設計する。** ライトで寒暖を割ると
体表シェーダの固定光源とズレてキャラが合成写真のように浮く。

ブルームを上げるなら `threshold` を下げるのではなく `strength` を微増。
しきい値を下げると加算VFXと重なった瞬間に飽和する。

### 押せるかどうかを判定する時

**`.click()` で判定しないこと。** プログラム実行なので、覆われていても成功してしまう。
必ず `elementFromPoint` で見る。ボタンは中心だけでなく上端・下端の3点を見ると、
部分的な潜り込みも拾える。

### エージェントを並行で走らせる時

- 常駐サーバは `HARNESS_VITE_PORT` と `HARNESS_PORT` を必ず指定する。
  自分のポートは `curl -s http://127.0.0.1:<制御ポート>/health` で確かめること
  (起動ログには他系統の番号が混ざることがある)
- 止める時は自分のポートだけ(`lsof -ti :<port> | xargs -r kill`)。
  **`pkill -f harness.mjs` は絶対に打たない**(他系統まで巻き込んで落とした事故がある)
- **作業ツリーは他系統の未コミット編集で汚れる。** 書きかけのファイルがそのまま読み込まれ、
  `TypeError` が連発してアプリが動かなくなることがある。
  **ブラウザ確認が突然壊れたら、まず `git status` で担当外のファイルを見ること。**
  自分の変更のせいだと誤診すると時間を溶かす
- scratchpad は全系統で共有されている。ログや画像のファイル名は自分用に分けること
- **指示書を作る時は必ず最新のコミットを確認すること。** 古い引き継ぎメモから指示を作り、
  既に完了済みの項目を再度指示してしまった事例がある

### 生成サービスと外部ツール

- **生成サービス(ElevenLabs / Suno / Meshy / Tripo など)は使えない。**
  この環境に API キーが無い。キーをもらえれば使える
- PyPI と apt には到達できる(`sudo` も `apt-get` もある)
- **Blender は pip で入る**(`bpy` 5.0.1、GUI無しの Python モジュール版)。
  ブーリアン・ベベル・ディスプレイス・リメッシュが使え、GLB へ書き出せる。
  「丸をつなげた雪だるま」問題への本命の解決策だが、**依頼主が一度見送っている**。
  要望が出たら再提案すること

## クラウドバックアップのセッション(片付いた。触る時の罠だけ残す)

依頼主の「かどさんはログインしているはずなのにサーバーに保存されていません」。

**原因はセッションの期限切れ。**サーバ側(`crimon-recovery`)のセッションは
**発行から30日**で、**使っても延びなかった。**切れると手元では:

- `loadCloudMeta()` が null を返す
- 自動バックアップが `if (!meta) return;` で**何も言わずに終わる**
- ホームの警告も出ない(`hasCloudRecoveryAccount` は期限を見ない)
- 設定を開くと**未登録の人と同じ画面**——「登録が消えた」ように見える

つまり**何も起きていないように見えたまま、ひと月ぶんがサーバへ届かない。**

直したのは4つ:

1. **サーバが使うたびに期限を延ばす**(`requireSession`)。残りが半分を切った時
   だけ書き戻す(毎回だと遊んでいる間ずっと `UPDATE` が走る)。
   延ばした期限は `sessionExpiresAt` で返し、手元も一緒に進める
2. **期限を見ない読み方**(`readCloudMeta` / `isSessionExpired`)を足した。
   `loadCloudMeta` は切れていると null を返すので、**未登録と区別が付かない**
3. ホームの警告を3つに分けた(`cloudRecoveryWarning`)。
   **期限切れの人に「登録がまだです」と言わない**(登録は消えていない)
4. 期限切れ専用の画面を作った

### ここは絶対に間違えない: 上書きの向き

期限切れの人を「以前のデータを復旧」へ流してはいけない。あちらは
**クラウドの控えを端末へ入れる**道で、切れている人のクラウド側は
**切れた時点の古い控え**。押させると**その後に遊んだぶんが丸ごと消える。**

`renderExpired` は逆をやる——ログインして新しいセッションを受け取り、
**手元のデータをそのままクラウドへ上げる**(`storeCloudMeta` → `syncNow`)。
`tests/cloudSessionExpiry.test.ts` が `restoreCloudSave` / `previewRestore` が
混ざったら落とす。

### `crimon-recovery` もリポジトリへ入れた

`.github/workflows/recovery-edge.yml` で main から自動deploy。
**Supabase の画面から直接編集しないこと**(次に main が動いた時に消える)。

### 種を渡さない戦闘テストは、確率でCIを赤くする

`tests/stageRunner.test.ts` が、クラウドバックアップだけを直したPRで落ちた。
**戦闘には1行も触っていない。**

`BattleEngine` は `this.rng = options.rng ?? Math.random` なので、
**種を渡さないと実行のたびに違う戦闘**になる。1-1の敗北率を2万回で測ると
0.01%(2回)。30回全勝を要求していたので、**1回の実行あたり 0.30% で落ちる**
——300回に1回、無関係な変更のCIが赤くなる。

いまは30通りの種を固定してある。**乱数の流れを30通り見る**という元の狙いは
そのままで、結果だけが揺れなくなる。
**戦闘を回すテストを足す時は、必ず `rng` を渡すこと。**

## アリーナのアカウントが2つに分かれる(調査済み。同じ調査を二度やらない)

依頼主の指摘:「荒モンボス猿さんが2人になってしまっています」。

**アリーナの身元は端末の localStorage (`crimon.arena.auth.v1`) にしかない。**
クラウドの控えにもセーブファイルにも入らないので、

- 端末やブラウザを変えた
- サイトデータが消えた(iOS Safari は訪問が途切れると消すことがある)
- **クラウド復旧で別端末へ移した**

のどれかで新しい匿名ユーザが生まれ、名前はセーブから来るので**同じ名前で2人**になる。
アプリ内で身元を捨てる経路は無い(`clearArenaAuth` はどこからも呼ばれていない)。
`arenaAuth.ts` は refresh token がある限り新規作成しない作りなので、
**保存が消えた時だけ**生まれる。

### user_id を持つ表(2026-09-22 時点・本番から取得)

**`arena_profiles.user_id` が親で、9つが CASCADE で参照している。**
統合する時に1つでも漏らすと、成績やコインが置き去りになる。

| 表 | 主キー | 統合時 |
|---|---|---|
| `arena_profiles` | user_id | 親。最後に消す |
| `arena_defenses` | user_id | 衝突する |
| `arena_standings` | user_id, season_id | 衝突する |
| `arena_wallets` | user_id | 衝突する |
| `trial_tower_progress` | user_id | 衝突する |
| `arena_season_results` | season_id, user_id | 衝突する |
| `arena_reward_claims` | id (UNIQUE user_id,kind,period_key) | 衝突する |
| `personal_gifts` | id (UNIQUE user_id,gift_key) | 衝突する。FKは無い |
| `arena_matches` | id | attacker=CASCADE / defender=SET NULL |
| `arena_match_sessions` | id | FKは season_id だけ |
| `arena_shop_purchases` | id | 付け替えるだけ |

`arena_opponent_pool` / `arena_public_ranking` / `trial_tower_public_ranking` は
ビュー(列が全て nullable で主キーが無い)。付け替え不要。

### 本番のSQLを流す道はある

`arena-catalog.yml` が `SUPABASE_DB_PASSWORD` で psql を叩いている。
接続は Session pooler で、利用者名は `postgres.<ref>`(`postgres` だけだと弾かれる)。
**`crimon_recovery_accounts` も `arena_*` も migration に無い**(Supabase 上で
直接作られた)ので、`db push` は使えない。**冪等なSQLを名指しで流すこと。**

### 分かれたアリーナアカウントを合わせる道具

`supabase/migrations/20260922090000_arena_merge.sql` に
`crimon_arena_merge(p_from, p_to, p_dry_run)` がある。
管理者画面の「アリーナアカウントを合わせる」から呼ぶ。

**押す前に必ず「こうなります」を見ること。**実行の側は
**移し先の表示名を打たないと通らない**(一覧の押し間違いで本番が動かないように)。
実行前の姿は `crimon_arena_merge_log.before_snapshot` に丸ごと控える。

合わせ方:

| もの | どうするか |
|---|---|
| レート・最高レート | **高い方** |
| 勝敗(攻撃・防衛) | **合算** |
| コイン・累計コイン | 合算 |
| 挑戦券 | 合算しない(持てる数なので**多い方**) |
| 塔の到達階 | 高い方と、**その階に着いた方**の時刻 |
| 防衛編成 | **新しい方を残す**(古い編成はいま持っていないモンスターが並ぶ) |
| 受け取り記録・個別配布 | **衝突したら残す**(移すと二重受け取りになる) |
| 登録日 | **古い方**(いつから遊んでいるかが消える) |

**親(`arena_profiles`)を消すのは最後。**先に消すと9つの子が CASCADE で
道連れになる。`tests/arenaMerge.test.ts` が順序を見張っている。

#### 手元で本当に動かして確かめられる

`psql` が入っている。本番と同じ形(列・主キー・**CASCADE**)を作れば、
実際に合わせて結果を見られる。Supabase 固有のロールが要る:

```
su postgres -s /bin/bash -c "/usr/lib/postgresql/16/bin/initdb -D /var/tmp/crimonpg -A trust"
su postgres -s /bin/bash -c "/usr/lib/postgresql/16/bin/pg_ctl -D /var/tmp/crimonpg -o '-p 5433 -k /var/tmp' start"
psql -h /var/tmp -p 5433 -U postgres -c "create role anon; create role authenticated;"
```

**`/tmp` の下には作れない**(権限で initdb が落ちる)。`/var/tmp` を使うこと。

#### `security definer` は `search_path` を空にする

`set search_path = public` と書いて `tests/arenaSecurity.test.ts` に落とされた。
空にした上で、**すべてのオブジェクトを `public.` で修飾する。**
空にしないと、呼ぶ側が同じ名前の関数を自分のスキーマへ置くだけで
定義者の権限で走ってしまう。

## 試練の塔の記録が、サーバへ届いていなかった(片付いた)

依頼主の指摘「試練の塔も99階までいっているはずです」。管理者画面では**69階**。

原因は送る回数ではなく、**送るきっかけと、失敗の扱い**だった。

- 後者は**ランキングを開かない人には一生訪れない**

つまりクリアした瞬間に通信がこけると、その階は永久に届かない。

直した形(`src/web/main.ts` / `src/web/views/trialTower.ts`):

- **塔の画面を開くたびに送る**(`case "TRIAL_TOWER"` の先頭)。塔で遊ぶ人は必ず通る
- 送れなかった階を `state.towerSyncPending` に覚えて、塔の画面に出す
- サーバ側は低い階では上書きしないので、何度送っても害は無い

### 触る時の罠

- **`case "TRIAL_TOWER"` は `render()` の中。**素直に送ると描き直しのたびに
  RPCが飛び、しかも `render()` を呼び返す。`towerSyncSentFloor`(届いた階)・
  `towerSyncRunning`(重ねない)・`TOWER_SYNC_RETRY_MS`(失敗時の間隔)の3つで止めている
- **`arenaSyncAvailable()` が偽の時は pending を立てない。**通信の失敗ではなく、
  ランキングそのものが無い環境というだけ。立てると直しようのない警告が出っぱなしになる
- **案内(`.tower-notice`)を2枚並べない。**広い画面では `.tower-screen` が格子で、
  `.tower-notice` の `grid-row` が名指し。2枚出すと同じ枡に重なる。
  `renderNotices()` が1枚の中へ行(`.tower-notice__line`)として積む
- 巡回に `試練の塔(記録が届いていない)` を足した。DEVの口は
  `window.__crimonDev.showTowerSyncPending(99)`。`navigate()` が案内を畳むので、
  **立てるのは `navigate()` の後**

### まだ確かめていないこと

**なぜ69階で止まったのか(通信断か、別の理由か)は特定できていない。**
サーバ側RPC(`trial_tower_submit_progress`)・クライアント側の検め(1〜100)・
`trialTowerLifetimeBestFloor` の引き継ぎは、いずれも読んだ限り正しい。
今回の直しは「どの理由で落ちても追いつく」形にしたもの。
**依頼主に一度塔の画面を開いてもらえば、そのまま正しい階へ直る。**
直らなければ、原因は送信以外(アカウントが分かれている等)にある。

  (mainと同じ種で比べて一致を確認済み)。**`acc` を常に作る形へ変えると、既存の戦闘の乱数がずれる。**

- セーブの圧縮(`saveCodec.ts`)は**モンスターの項目を列挙している。**
  `accessoryId` は `g`、限界配分は育成の `z`。新しい項目を個体へ足したら、ここにも足すこと。
- 遺跡は**装備ダンジョンと同じダンジョン編成(最大5体)**で戦う(依頼主の指定)。
