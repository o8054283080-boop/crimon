# バトル画面 ビジュアル品質ルーブリック

バトル画面(Three.jsによる3D描画)の見た目を、主観の言い合いにせず繰り返し判定できるようにするための採点基準。
スクリーンショットを撮ってこの基準で採点し、基準点に届かない項目を次の改善サイクルの対象にする。

撮影は `SHOOT_PORT=<ポート> node tools/shoot.mjs <出力ディレクトリ>` で行う。
縦長(430x932)と横長寄り(900x1200)の両方を撮り、**両方で成立していること**を必須とする。

## 前提と限界

- 実在の商用タイトルのクライアントを起動して並べる「実機ブラインド比較」は行わない(実行環境で不可能であり、
  他社アセットに寄せること自体を目的にもしない)。
- 判定は「一般的なハイエンド・モバイルRPGのバトル画面として通用するか」を基準に、以下の観点で行う。

## 採点項目(各5点満点)

### 1. シルエットの可読性
- 5: 各モンスターが一目で「生き物/存在」として認識でき、役割(前衛・支援・ボス)がシルエットだけで区別できる
- 3: 形状の差はあるが、何であるかは読み取りにくい
- 1: 光る塊・単純な幾何形状にしか見えない

### 2. 構図とフレーミング
- 5: 両チーム全員が対等に読め、手前が巨大化しすぎず、画面端で切れていない。縦長でも横長でも成立
- 3: 一部が小さすぎる/大きすぎる、あるいは片方の画面比率でのみ成立
- 1: キャラが見切れる、重なって判別できない

### 3. ライティングと立体感
- 5: キー/フィル/リムが効き、輪郭が背景から分離。陰影に方向性があり立体として読める
- 3: 明るさはあるが平坦、または陰影の方向が不自然
- 1: のっぺりしている、または真っ黒/真っ白に潰れている

### 4. 露出とポストプロセス
- 5: 発光部分だけが上品に滲み、白飛び・黒潰れがない。色調に統一感がある
- 3: 一部が飛んでいる、またはブルームが弱く平板
- 1: 画面の広い範囲が白飛びして形が消えている

### 5. 環境(ステージ)の説得力
- 5: 空・地面・遠景・大気に奥行きと物語性があり、闘技場として成立している
- 3: 背景はあるが安っぽい、または要素が唐突
- 1: 単色背景同然、あるいは意味不明な形状が置かれている

### 6. エフェクトの情報量と差別化
- 5: 攻撃/回復/バフ/デバフ/状態異常が見た目で区別でき、属性ごとに表現が違う
- 3: 種類の差はあるが、色違いの粒が飛ぶだけ
- 1: すべて同じエフェクト

### 7. 打撃感(インパクト)
- 5: 命中の瞬間に閃光・衝撃波・カメラシェイク・ヒットストップが噛み合い「効いた」と感じる
- 3: 何か起きたのは分かるが手応えが薄い
- 1: HPだけ減って何も起きていないように見える

### 8. アニメーションの生命感
- 5: 待機中も呼吸・揺れがあり、攻撃は予備動作→打撃→戻りの流れがある
- 3: 動いてはいるが単調な平行移動・回転
- 1: 静止画に見える

### 9. UI/HUDの品質
- 5: 情報階層が明快で、装飾のディテール(フレーム・グラデーション・光沢)が作り込まれている
- 3: 読めるが素っ気ない
- 1: 未装飾のHTML要素に見える

### 10. 全体の一体感
- 5: 3D・エフェクト・UIのトーンが揃い、ひとつの製品として見える
- 3: 個々は悪くないがちぐはぐ
- 1: 素材の寄せ集めに見える

## 合格ライン

- **各項目 4 点以上**、かつ **合計 42 点以上(50点満点)** を到達目標とする。
- 3 点以下の項目が 1 つでもあれば、その項目を次サイクルの改善対象として明示する。

## レビュー時の必須手順

1. スクリーンショットを撮る
2. **画像を実際に開いて見る**(コードを読んだだけの評価は無効とする)
3. 項目ごとに点数と、減点理由を具体的な語(どこがどう悪いか)で記述する
4. 「次に直すべき最重要の3点」を優先順位付きで挙げる
