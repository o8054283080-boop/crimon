# iPhoneの「ホーム画面に追加」が失敗していた理由

## 結論

**`public/icons/` のPNGが、途中で切れた壊れたファイルだった。**

manifest でも Service Worker でも meta でも JavaScript でも Cloudflare Pages でもない。
`apple-touch-icon` を指定した瞬間に失敗したのは、iOSがホーム画面へ追加する時に
**そのアイコンをデコードするから**で、デコードに失敗すると追加そのものが黙って失敗する。

## 切り分けの結果が指していたもの

依頼主の切り分けは正しく、そのまま答えを指していた。

| ページ | 結果 | 参照するアイコン |
| --- | --- | --- |
| `bare.html` | 成功 | 無し |
| `diag-meta.html` | 成功 | 無し |
| `diag-script.html` | 成功 | 無し |
| `diag-icon.html` | **失敗** | `./icons/apple-touch-icon.png` |

差分はアイコンの有無だけ。そしてそのアイコンが読めないファイルだった。

## なぜ「正常なPNG」に見えたのか

壊れ方が、確認しやすい部分をすべて素通りする形だった。

- PNG署名(先頭8バイト)…**正しい**
- IHDR(縦横・色の種類)…**正しい。180×180 / RGB / 非透過と読める**
- IDAT(画素データ)…**「11,981バイトある」と書いてあるのに、364バイトしか無い**

つまり「180×180のRGBで署名も正しい」という確認は全部通る。
画像ビューアによっては途中まで表示してしまうので、目でも気づけない。

## 歴代の版を全部デコードしてみた結果

`apple-touch-icon.png` を実際に展開して確かめたところ、**直したはずの版がほぼ全部壊れていた。**

| コミット | 内容 | サイズ | 判定 |
| --- | --- | --- | --- |
| `e1cca9f` | 最初の版 | 4,395B | ✅ 読める |
| `0a9a501` | 青いドラゴンへ刷新 | 15,009B | ❌ 途中で切れている |
| `39248a5` | iOS互換へ差し替え | 2,754B | ❌ 途中で切れている |
| `bb79243` | 新デザインへ差し替え | 16,648B | ❌ IDATのCRCが合わない |
| `059aa46` | Fix from original artwork | 14,962B | ❌ PNG署名すら無い |
| `c3c5a28` | Fix corrupted binary | 11,630B | ❌ 途中で切れている |
| `e6f1905` | minimal standard PNG | 405B | ❌ 途中で切れている |

manifest が参照する `icon-192.png` と `icon-512.png` も同じく途中で切れていた
(しかも中身が1バイト単位で同一で、宣言している大きさだけが違う)。
無事だったのは `favicon-32.png` だけ。

## なぜ壊れたのか

壊れ方が毎回同じ(**ヘッダは正しく、末尾が欠ける**)なので、
原因は**バイナリを文字として扱う経路を通したこと**とみてよい。
base64の一部しか書けなかった、途中のNULバイトで切れた、といった類。
1度なら事故だが、5回続いたので**経路そのものが壊れている。**

## 直し方

### 1. 元絵から焼く

`tools/bakeAppIcons.mjs` を足した。`src/web/assets/app-icon.png` を
Chromiumのcanvasで描き、**canvasが出したbase64をBufferで直接書き出す**。
途中に文字列としての加工が入らないので、同じ壊れ方をしない。

```
node tools/bakeAppIcons.mjs
```

元絵は透過つきなので、**必ず背景(`#171826`)を敷いてから描く。**
iOSはアイコンを角丸で切り抜くだけで、透過部分は黒く残る。
元絵自体が壊れていないことも `tests/pngIntegrity.test.ts` が見張っている
(`src/web/assets` も検査の対象)。

**アイコンを差し替える時は、`src/web/assets/app-icon.png` を置き換えて
この道具を回すだけ。** `public/icons/` のPNGを手で作らないこと——
5回壊れたのは、そこを手で作った時だけ起きている。

### 2. 壊れたら必ず落ちるようにする

`tests/pngIntegrity.test.ts` を足した。`public/` と `src/web/assets/` の
PNGを全部たどり、チャンクを最後まで読み、CRCを検算し、**IDATを実際に展開して
画素の量が縦×横と一致するか**まで確かめる。途中で切れていれば必ず落ちる。

このテストが本物を拾えることは、`e6f1905` の壊れた版を戻して確認した
(「IDATチャンクが11981バイトと書いてあるのに、残りは364バイトしかない」で落ちる)。

## iOS側のキャッシュについて

疑うのは自然だが、**今回の原因ではない。**

- `diag-icon.html` は新しく作られた別ページで、そのページとしては初回の追加だった
- リポジトリに入っているバイト列そのものが、どんなデコーダでも読めない

キャッシュが効いていたとしても、キャッシュされている中身が壊れているので結果は同じ。

## 残る確認

**本番(crimon.pages.dev)が配っているバイト列は直接見ていない。**
この環境からは外部への接続が塞がれているため。
Cloudflare Pages は `public/` をそのまま配るので、リポジトリのバイト列が
そのまま届いているはずだが、**確かめてはいない。**

差し替え後に `diag-icon.html` をもう一度追加してみて、成功すれば裏が取れる。
