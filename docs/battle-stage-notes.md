# バトルステージ(3D)の設計メモ

> ゲーム全体の設計コンセプト(何を面白さの芯に置いているか)は
> `docs/design-concept.md` にある。バランスや役割の判断はそちらを参照すること。

`src/web/three/` 以下の実装について、コードを読むだけでは分かりにくい前提と、
過去に踏んだ落とし穴を残しておく。演出を足す前にここを読むこと。

## 全体の構成

```
battleStage.ts   シーン・カメラ・ライティング・ポストプロセス・進行への接続
  arena.ts       闘技場(空・床・観客席・列柱・ゲート光・霞)
  monsterAvatar.ts  1体分のアバター。モーション付けに専念する
    creature/    役割別の骨格ビルダーと、体表シェーダ
  vfx.ts         戦闘演出。内部で fx/ の各フィールドを束ねる
    fx/          パーティクル・ビルボード・帯・状態異常オーラ
  postfx/        トーンマッピング後の仕上げ
```

`battleView.ts`(2D側)が進行を回し、`BattleStage` のメソッドを呼んで演出させる。
HUDはHTMLで、3D座標に毎フレーム追従させている。

## 加算合成の飽和について(重要)

戦闘演出はほぼすべて加算合成で描いている。加算合成は**重なった分だけ明るくなる**ため、
個々の演出が正しくても、同時に多く出た瞬間に画面全体が白く飛んで何も見えなくなる。

実際にこの不具合を出した。原因は単一ではなく、次のすべてが同時に効いていた。

1. 粒の画素サイズの式が `aSize * (300.0 / max(0.001, depth))` で、粒がカメラ近傍に
   来ると点が最大30万倍まで発散し、1粒で画面を覆っていた
2. クリティカルの閃光が12ワールド単位で、画面の縦(約9.6単位)より大きかった
3. 同時に生きている板が75枚、粒が700個を超えていた

対策として、演出側が何を指定しても破綻しないよう、共通の経路で頭打ちにしている。

- **粒**: 画素サイズに上限。カメラの手前・背後の粒は描画しない
- **板**: 画面の高さに対する占有率の上限。同時生存数の上限。混雑時は確率的に間引く
- **帯**: 同時生存数の上限。混雑時は確率的に間引く
- **共通倍率**: 大きさと濃さを、画面に映るワールド高さから自動で決める
  (`VFX_REFERENCE_HEIGHT` / `VFX_MAX_SCREEN_RATIO` / `VFX_DENSITY` / `VFX_OPACITY`)

### 演出を足す時の注意

新しい演出を足す場合、**個々の値を大きくして目立たせようとしないこと**。
上限に当たって効かないか、他の演出を押しのけるだけになる。
派手さが足りない時は、まず上記の共通パラメータを見直す。

## 見た目・操作を確かめる手順(重要)

**型チェックとテストは、CSSとWebGLの安全弁にならない。**
重なり順の誤り、`position` の指定漏れ、GLSLのコンパイル失敗、
束ね忘れによる実行時エラーは、`tsc --noEmit` も `vitest` も素通りする。
実際にこの経路で「モンスターが全員消える」「ステージが押せない」
「報酬が受け取れない」を出した。**必ず実ブラウザで確かめること。**

確認には常駐サーバを使う。Vite とブラウザを立ち上げたまま保つので、
2回目以降は数秒で終わる(起動し直す作りだと1回2〜8分かかっていた)。

```
node tools/harness.mjs &                       # 一度だけ起動して常駐させる
node tools/probe.mjs goto /                    # アプリを開く
node tools/probe.mjs goto /preview.html "seed=3&paused=1&roster=..."
node tools/probe.mjs shot /tmp/a.png .battle-stage
node tools/probe.mjs eval "window.__crimonStage.pickUnitAt(400, 200)"
node tools/probe.mjs tap 450 200
node tools/probe.mjs drag 450 200 -300         # カメラの回り込み
```

出力の `problems` が空でなければ、型チェックが通っていても壊れている。
`probe.mjs` はその場合に終了コード2を返すので、確認の自動化にも使える。

### 押せない・位置がずれる、を調べる時

見た目だけでは分からないので、DOMに直接聞く。

```
node tools/probe.mjs eval "(() => { const n = document.querySelector('.stage-tile'); const r = n.getBoundingClientRect(); const top = document.elementFromPoint(r.x + r.width/2, r.y + r.height/2); return { 自分が最前面か: n.contains(top) || n === top, 手前にあるもの: top.className }; })()"
```

「押せない」の正体はほぼ**別の要素が上に乗っている**か、
**`position: relative` の付け忘れで子要素が画面全体へ広がっている**かのどちらか。

### 切り分けの手順

画面が白い・何も見えない、といった描画の異常は `tools/diagnose.mjs` で調べる。
スクリーンショットは1回8分前後かかるが、この道具は約2分で
「各サブシステムの同時生存数」「カメラ位置」「各ユニットの投影座標」を数値で返し、
同じ状態のステージ画像も保存する(数値と画像のピクセル座標が一致する)。

```
node tools/diagnose.mjs <出力JSON> "seed=777&turns=4"
```

ポストプロセスを疑う場合は、`composer.render()` を
`renderer.render(this.scene, this.camera)` に一時的に差し替えると、
素の描画と仕上げ後を比較できる。

## カメラのフレーミング

画角は望遠寄りに固定し、足りない分は引いて稼ぐ方針。`frameCamera` が
「両チームが必ず収まる最短距離」を二分探索で求めてカメラを置く。

- 見下ろし角を浅くすると、前後の列が画面上で潰れて重なる。18〜27度を確保している
- 遠くの列は透視投影で中央へ詰まるため、敵の列だけ横間隔を広げて打ち消している
  (`ENEMY_SPREAD`)
- 縦画面でステージを縦長にすると、闘技場の壁が画面中央に黒い帯として入る。
  横向きの方がこのゲームの構図には合う

## 体表の見え方

モンスターは外部の3Dモデルを持たず、すべてプロシージャル生成。
シルエットは**役割**で決まり、そこへ**種別固有の造形**(翼・光輪・羽根飾り)を足している。
役割だけで決めると、同じ役割の別モンスターが色違いにしか見えなくなる。

体表は単色だとプラスチックに見えるため、フラグメントシェーダで
色ムラ・鱗・金属の筋・擬似AOを計算している。模様はワールド座標基準で描いており、
パーツごとに大きさが違っても粗さが揃う。

## 造形の方針: 球を積むのをやめる(重要)

依頼主の指摘: **「丸をつなげた雪だるまみたいのが多い」**。
これは的確で、原因は `kit.ball()` で球を並べて繋ぐ組み方そのものにある。
球は輪郭がどこを切っても円弧なので、いくつ並べても「丸の連なり」にしかならない。
色や質感をどれだけ磨いても、この構造のままでは商用作品の水準に届かない。

参考として示された高レアのドラゴンから読み取れる、効いている要素は次の6つ。

1. **積層した板**。胸・腹が、下から上へ少しずつ重なる帯(シェブロン)の積み重ねでできている。
   1枚1枚に縁があるので、面が平らでも情報量が出る
2. **面取りされた角**。丸ではなく、稜線のある多面体。光が面ごとに切り替わるので形が読める
3. **結晶の房**。肩・背・尾・肘に、大小の尖りが**群れとして**生えている。
   1本ずつ均等に生やすと櫛になるので、束ねて大小を混ぜる
4. **骨の見える翼**。指の骨が膜を張っている構造が見えている。膜だけだと布になる
5. **細い腰と重い肩**。上半身に質量を寄せ、腰でくびれる。丸を並べると寸胴になる
6. **末端の硬さ**。爪・牙・角の先が鋭い。丸い先端は玩具に見える

### 具体的にやること

- `kit.ts` に**球以外の語彙**を足す。積層板・面取り角柱・結晶の房・骨組み付きの膜
- 既存ビルダーの `kit.ball()` を、部位の性格に応じて置き換える。
  ただし**すべてを角張らせない**。粘体(スライム)や小動物は丸くてよい。
  角張らせるべきは、竜・魔王・岩・甲殻など「硬いもの」
- 輪郭は**シルエットだけで種別が分かるか**で判定する。塗りを消した黒い影で見て確かめること
